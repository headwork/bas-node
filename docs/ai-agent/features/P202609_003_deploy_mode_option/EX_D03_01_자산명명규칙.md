# `[D03]` 관리 자산 명명 규칙 (#P202609_003)

정본은 [spec.md](spec.md). **보스 예시의 `./project1_org` 등은 이해를 돕기 위한 임시 이름이고,
이 문서가 현재 규약에 맞춰 조정한 실제 이름이다.**

## 1. 축 — 한 배포는 스탬프 하나를 쓴다

`stamp = YYYYMMDD_HHMMSS` (충돌 시 `_N`, [backupRetention.js:110-127](../../../../src/deploy/backupRetention.js#L110-L127))

배포 한 번이 만드는 것은 최대 4개이고 **전부 같은 스탬프를 쓴다.** 그래야 로그·이력·폴더가
한 줄로 묶이고, 사람이 긴급 상황에서 고를 때 짝을 찾지 않아도 된다.

```
20260923_165347  →  MFM.Shore_QA_temp_20260923_165347      (스테이징)
                    MFM.Shore_QA_org_20260923_165347       (밀려난 옛 라이브, 스왑만)
                    MFM.Shore_QA_preserve_20260923_165347  (유지파일 백업)
                    MFM.Shore_QA_20260923_165347.zip       (확정 빌드)
```

## 2. 자리

```
D:\Deploy\                                   배포 루트
  MFM.Shore_QA                               ← 라이브 (web_deploy_path)
  MFM.Shore_QA_temp_<stamp>                  스테이징              [기존]
  MFM.Shore_QA_org_<stamp>                   밀려난 옛 라이브       [신규]
                                             └ 스왑~헬스체크 사이의 복구 수단이자 델타 원본
  MFM.Shore_QA_failed_<stamp>                롤백이 치운 실패본     [기존]
  MFM.Shore_QA_replaced_<stamp>              강제 롤백이 밀어낸 것  [기존]

D:\HLNGS\backup\                             backup_root
  MFM.Shore_QA_preserve_<stamp>\             유지파일 백업          [신규]
  _builds\MFM.Shore_QA_<stamp>.zip           확정 빌드 = 롤백 원본  [신규]
  config\qa\                                 config_backup         [기존]
  MFM.Shore_QA_<stamp>\                      전체 폴더 백업        [폐지 예정]

D:\HLNGS\build\                              upload_path
  MFM.Shore_QA.zip                           작업용 zip (매번 덮어씀) [기존]
  _scripts\qa\windows\                       배포 스크립트          [기존]
```

* **`_org_` 에 스탬프를 붙인다.** 보스 예시는 `project1_org` 였다. 스탬프가 없으면 헬스체크 전에
  다음 배포가 들어오거나 정리가 밀렸을 때 이름이 겹치고, `move` 는 **기존 폴더 안으로 들어가
  성공한 것처럼 보인다**([backupRetention.js:113-118](../../../../src/deploy/backupRetention.js#L113-L118) 이 같은 함정을 기록하고 있다).
* **확정 zip 은 `_builds\` 하위에 둔다.** 이름(`<live>_<stamp>`)이 폐지 예정인 폴더 백업과 같아서,
  같은 자리에 두면 보관 정책이 둘을 구분하려고 확장자에 의존하게 된다. 폴더를 가르면 그 판단이 필요 없다.
* **유지파일 백업은 라이브 옆이 아니라 `backup_root`** 다. 라이브 옆에 두면 현재 정리 대상 패턴
  (`<live>_<14자리>`)에 안 걸려 **영원히 쌓인다.**

## 3. 생애 — 언제 생기고 언제 사라지나

| 이름 | 생성 | 소멸 |
|---|---|---|
| `_temp_<stamp>` | 압축해제 | copy: 확정 시 / swap: 라이브가 되면서 사라짐 |
| `_org_<stamp>` | 스왑 | **헬스체크 통과 후** (확정 단계) |
| `_preserve_<stamp>` | 백업 **겸 이월 원본** (정지 전) | 보관 정책 `keep_count` |
| `_builds\*.zip` | **확정 시** | 보관 정책 `keep_count` = `--rollback=N` 상한 |
| `_failed_` · `_replaced_` | 롤백 | 다음 배포 성공 시 |
| `<live>_<stamp>\` (폴더 백업) | — | **3단계 전환 완료 후 폐지** |

⚠️ **"파일명·폴더명 변경은 헬스체크 이후"** (2026-09-23 보스 지시)에 따라 확정 단계가 필요하다.
현재는 원격 백업 정리가 **배포 직후·헬스체크 전**에 돈다
([RemoteDeployMacroStage.js:301-305](../../../../src/deploy/stages/RemoteDeployMacroStage.js#L301-L305)) — 이 정리도 확정 단계로 옮긴다.

## 4. 확정 단계 (`confirm`)

헬스체크 다음에 스테이지 하나를 둔다. **이름을 바꾸고 지우는 일은 전부 여기 모인다.**

```yaml
- health_check: { group: deploy, if: server_restarted }
- confirm:      { group: deploy, if: deployed }        # 신규
```

| 하는 일 | 대상 |
|---|---|
| 확정 | 작업용 zip → `_builds\<live>_<stamp>.zip` · 유지파일 백업 확정 |
| 삭제 | `_org_<stamp>` · copy 모드의 `_temp_<stamp>` |
| 정리 | 보관 정책 적용(zip · preserve) · `_failed_`·`_replaced_` 잔여 청소 |

**확정 전에는 아무것도 지우지 않는다.** 헬스체크가 실패하면 그 자리의 것들이 곧 복구 수단이다.
