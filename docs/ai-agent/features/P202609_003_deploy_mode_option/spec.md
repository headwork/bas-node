* **선행 작업**: [#P002 배포 대상 범용화](../P202609_002_deploy_target_abstraction/spec.md) — `deploy.bat` · `rollback.bat` · `scriptExit.js` 계약이 이 과제의 기반이다
* **선행 문서**: [06 배포 스크립트 규약](../../../design/배포/06_배포_스크립트_규약.md) · [02 운영 배포 흐름](../../../design/배포/02_운영_배포_흐름.md)

## 1. 개요

* **목적**: 배포 방식을 **복사(copy)** 와 **스왑(swap)** 둘로 나누어 환경별로 고르게 하고, `preserve` 를
  성격별로 분류해 백업 비용과 유실 위험을 분리한다.
* **문제**: 스왑 방식은 라이브 폴더를 `move` 하므로 **누가 그 폴더를 열고 있으면 배포가 계속 실패한다.**
  2026-09-22 QA 배포(`plWesysDeployNode#15`)가 이 사유로 실패했다 — `[deploy] failed to move live to backup`
  + `액세스가 거부되었습니다`. 라이브는 이전 빌드로 살아남아 서비스 영향은 없었다.
* **적용 방침 (보스 확정)**: **운영 = 복사**(기존 `wesys_restart.bat` 의 검증된 동작) ·
  **QA = 스왑**(실패해도 영향이 없어 새 방식의 검증장이 된다).

## 2. 미결 항목 (OQ)

* ~~`#P003-OQ1` 복사 방식의 롤백 사본~~ → **확정 (2026-09-23). 백업은 `유지파일 + 배포 zip` 둘이다.**
  라이브 폴더 사본을 뜨지 않는다. 상세 [`EX_D01_01` §4](EX_D01_01_배포방식설계.md#4-백업과-롤백--p003-oq1-확정).
* ~~`#P003-OQ2` 삭제된 파일 반영~~ → **확정. 미러하지 않는다.** 누적된 옛 파일은 **스왑 방식으로 한 번
  배포하면 사라진다**(폴더를 통째로 갈아끼우므로). 운영에서 일회성 스왑이 필요하므로 `--mode` 를 둔다(#P003-REQ8).
  ⚠️ 전제: 빌드가 **clean 빌드**여야 한다. 누적 빌드면 zip 자체에 옛 DLL 이 들어가 스왑으로도 안 지워진다 → `#P003-OQ4`.
* ~~`#P003-OQ3` 스왑 성공 시 기존 폴더 삭제~~ → **확정. 삭제한다.** OQ1 로 zip 이 백업 역할을 하므로
  `<live>_org` 는 롤백의 근거가 아니다. **단 삭제 시점은 헬스체크 통과 후다**(그 전까지는 역스왑이 가장 빠른 복구다).
* ~~`#P003-OQ4` clean 빌드 여부~~ → **확정 (2026-09-23). 도구가 검사하지 않는다.**
  clean 빌드 옵션은 나중에 별도로 추가한다. 누적 빌드로 스왑 배포한 것은 **사용자가 인지하고 있는 선택**이므로
  가이드 문서에 clean · 누적의 차이만 설명한다(#P003-REQ11).

**미결 없음.** 아래 REQ 로 전부 확정됐다.

## 3. 주요 기능 및 요구사항 (REQ)

* `#P003-REQ1`: **`deploy_mode: copy | swap` 옵션 추가.** 기본값 `copy`, 환경(`server_info`)별 지정.
* `#P003-REQ2`: **preserve 3분류** — `temp`(재생성 가능) · `data`(유실 불가) · `config`(설정).
  분류마다 배포 방식별 처리가 다르다. 현재의 평면 목록 `preserve` + 별도 `preserve_config` 를 흡수한다.
* `#P003-REQ2b`: **swap 의 이월을 벌크와 델타로 가른다** — 벌크는 **정지 전**(서비스 가동 중),
  `_org_` 에서 따라잡는 델타만 정지 구간에서. 현재는 정지 후 전량 복사라 `temp` 가 크면 그대로 다운타임이다.
  **델타는 시작 _전_에** 밀어넣는다(시작 후면 방금 쓰인 파일이 잠깐 없는 상태가 된다).
* `#P003-REQ3`: **복사 방식 구현** — 정지 → 백업 → robocopy 덮어쓰기 → 시작.
  preserve 를 **옮기지도, 되돌리지도 않는다**(라이브에 그대로 있고 미러가 아니라 지워지지도 않는다).
  복사 제외는 `config` 하나뿐이다 — 스왑의 Step 2.5 를 대신하는 자리다. [`EX_D01_01` §3.1](EX_D01_01_배포방식설계.md#31-copy-모드에서-제외는-config-하나뿐이다)
* `#P003-REQ4`: **백업은 `유지파일 + 배포 zip` 이다** (OQ1 확정). 라이브 폴더 사본을 뜨지 않는다.
  배포 성공(헬스체크 통과) 시 그 시점의 zip 을 **세대로 확정**하고, 롤백은 그 zip 을 다시 전개한다.
  확정 zip 의 보관 세대 수가 곧 `--rollback=N` 의 상한이다.
* `#P003-REQ5`: **잠금 견고화 (두 방식 공통)** — ① IIS 정지 후 워커 프로세스(w3wp) 종료 대기
  ② 실패 시 폴더를 잡고 있는 프로세스를 로그에 남김 ③ 원격 stderr 인코딩(CP949) 정정.
* `#P003-REQ6`: **하위호환** — `preserve:` · `preserve_config:` 를 쓰는 기존 YAML 이 수정 없이 동작한다
  (#P002-REQ5 와 같은 원칙). 기존 `preserve` 는 `data` 로, `preserve_config` 는 `config` 로 승격.
* `#P003-REQ7`: **QA YAML 에 `deploy_mode: swap` 을 명시한다.** 기본값을 `copy` 로 두면
  적지 않은 QA 가 조용히 복사 방식으로 바뀐다 — 에러가 나지 않으므로 사람이 눈치채지 못한다.
* `#P003-REQ8`: **`--mode=copy|swap` CLI 오버라이드.** 운영의 누적 파일 청소(OQ2)를 위해
  일회성으로 스왑을 돌릴 수 있어야 한다. 그때 YAML 을 고치게 두면 고친 채로 남는다.
* `#P003-REQ9`: **확정 단계(`confirm`) 신설** — **이름을 바꾸고 지우는 일은 전부 헬스체크 뒤에 모은다**
  (2026-09-23 보스 지시). 현재는 원격 백업 정리가 배포 직후·헬스체크 전에 돈다.
* `#P003-REQ10`: **롤백을 두 트랙으로 가른다** — 트랙 A(배포중 원복, 미확정) · 트랙 B(확정 후 롤백).
  가르는 기준은 **확정 여부**다. 구현은 한 벌이고 방아쇠만 둘이다. [`EX_D04_01`](EX_D04_01_롤백두트랙.md)
* `#P003-REQ11`: **관리 자산 명명 규칙을 문서로 고정한다.** 배포 하나가 폴더·파일 4개를 만들고
  생애가 제각각이다. 규칙이 없으면 정리 대상에서 빠진 것이 조용히 누적된다. [`EX_D03_01`](EX_D03_01_자산명명규칙.md)

### 결정 사항

* **IIS 물리 경로 전환 방식은 채택하지 않는다** (2026-09-23 보스 확정). 잠금 문제에서 자유롭지만
  라이브 경로가 매번 바뀌어 설정 보전·백업 정리·롤백이 모두 "현재 경로를 IIS 에 묻는" 구조가 된다.
* **정적 배포(`static_patch`)는 이 과제의 범위 밖이다.** 이미 복사 방식이고 정지도 백업도 없다.
