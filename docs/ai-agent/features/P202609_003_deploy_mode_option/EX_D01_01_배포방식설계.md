# `[D01]` 배포 방식 설계 (#P202609_003)

정본은 [spec.md](spec.md). 이 문서는 시퀀스 · 분류 · 선택지만 담는다.

---

## 1. 두 방식의 시퀀스

### copy — 기존 폴더에 덮어쓴다 (운영 기본)

```
① 백업          preserve 분류에 따라 (§3)          ← 정지 전. 라이브는 아직 살아 있다
② 정지          webserver stop + w3wp 종료 대기
③ 복사          robocopy 배포본 -> 라이브          ← config 만 제외 (§3.1)
④ 시작          webserver start
```

**preserve 를 옮기지 않는다.** 라이브에 그대로 있고, 미러가 아니므로 robocopy 가 지우지도 않는다.
스왑이 preserve 를 이월하는 것은 **폴더가 통째로 바뀌기 때문**이지 이월 자체가 목적이 아니다.

* **폴더를 옮기지 않으므로 잠금에 강하다.** 탐색기·cmd 가 그 폴더를 열고 있어도 덮어쓰기는 된다.
* 개별 파일을 잡고 있으면 그 파일에서 실패한다(w3wp 미종료·로그 tail). → `#P003-REQ5` 가 필요한 이유.
* robocopy 는 같은 파일을 건너뛰므로 실제 복사량은 바뀐 파일뿐이다. 다만 매 빌드에서 다시 컴파일되는
  DLL 은 타임스탬프가 달라 항상 복사된다 — 정적 자산만 절감된다.
* ⚠️ **중간 실패 시 라이브가 옛 빌드와 새 빌드가 섞인 상태로 남는다.** 스왑에 없던 상태다(§4).

### swap — 폴더를 갈아끼운다 (QA)

```
① 백업/이월     preserve(temp+data+config) -> <live>_preserve_<stamp>   ← 정지 전. 서비스 살아 있음
② 임시폴더      압축해제 -> <live>_temp_<stamp>
③ 이월          <live>_preserve_<stamp> -> 임시폴더                      ← 정지 전. **벌크는 여기서 끝난다**
④ 정지          webserver stop + w3wp 종료 대기
⑤ 스왑          live -> <live>_org_<stamp>, staged -> live               ← 이 사이에 라이브가 없다
⑥ 델타          <live>_org_<stamp> 의 temp+data 중 **그 사이 늘어난 것**만 밀어넣기
⑦ 시작          webserver start
```

**정지 구간이 rename 2회 + 델타로 줄어든다** (2026-09-23 보스 안).
현재 [deploy.bat:216](../../../../bundle_config/deploy/script/windows/deploy.bat#L216) 은 이월을 **정지 후에
`robocopy /E` 전량**으로 한다 — `temp` 가 크면 그만큼 서비스가 내려가 있다.

세 가지가 순서로 결정된다.

* **③(벌크)은 정지 전.** 서비스가 살아 있어도 된다 — 어차피 ⑥이 그 뒤의 변경을 따라잡는다.
* **⑥(델타)은 시작 _전_.** 시작 후에 밀어넣으면 방금 업로드된 파일이 잠깐 없는 상태가 되어 404 가 난다.
* **`_org_` 삭제는 ⑥ 직후가 아니라 헬스체크 이후.** 델타를 밀어넣어도 `_org_` 원본은 그대로라,
  헬스체크가 실패하면 역스왑이 여전히 가장 빠른 복구다.

델타 판정은 `robocopy <org>\<name> <live>\<name> /E /XO` — 벌크는 타임스탬프가 같아 건너뛰고
그 사이 쓰인 것만 넘어간다. 목록을 비교할 필요가 없다.
⚠️ 시계가 틀어진 서버에서는 `/XO` 가 새 파일을 건너뛸 수 있다. 정지 구간이라 쓰는 쪽은 없으므로
누락되면 다음 배포에서 다시 잡힌다 — `temp` 는 재생성되고 `data` 는 `_preserve_` 백업에 남아 있다.

## 2. 모드 선택

```yaml
server_info:
  deploy_mode: copy      # copy(기본) | swap
```

| 환경 | 값 | 이유 |
|---|---|---|
| 운영 | `copy` (생략 가능) | 기존 `wesys_restart.bat` 이 하던 동작. 잠금에 강하다 |
| QA | `swap` **명시 필수** | 실패해도 영향이 없어 새 방식의 검증장. 적지 않으면 기본값 `copy` 로 조용히 바뀐다 |

## 3. preserve 분류 — 백업 정책이 갈리는 지점

현재는 `preserve`(평면 목록)와 `preserve_config`(별도 키) 둘뿐이라 **크기와 복구 가능성이 다른 것들이
같은 정책을 받는다.** 업로드 폴더와 캐시 폴더가 같은 취급을 받는 것이 문제다.

| 분류 | 예 | 유실되면 | copy 시 | swap 시 |
|---|---|---|---|---|
| `temp` | `Temp`, 캐시 | 다시 만들어진다 | 그대로 둔다 | 이월(벌크) + 델타 |
| `data` | `uploads`, 다운로드 | **복구 불가** | 그대로 둔다 | 이월(벌크) + 델타 |
| `config` | `web.config`, `appsettings.json` | 서비스가 안 뜬다(500.19) | **복사 제외** | 이월 + `config_backup` 갱신 |

**`_preserve_<stamp>` 는 백업이자 이월 원본이다.** 그래서 재생성 가능한 `temp` 도 담는다 —
"백업할 가치"가 아니라 **"새 배포본에 있어야 하는가"** 가 기준이다.
`config` 는 런타임에 아무도 쓰지 않으므로 델타가 없다.

> 📌 일반적으로 `temp`·`upload` 는 배포 폴더 밖의 별도 스토리지에서 관리된다.
> 이 프로젝트는 `Temp` 만 폴더 안에 있고 업로드는 없다. `data` 가 커져서 느려지는 경우는
> **사용자가 인지하고 선택한 구성**이므로 설계에서 따로 다루지 않는다 (2026-09-23 보스 확인).

```yaml
preserve:
  temp:   ["Temp"]
  data:   ["uploads"]
  config: ["web.config", "appsettings.json"]
```

**하위호환**: 기존 평면 목록 `preserve: ["uploads", "Temp"]` 는 전부 `data` 로,
`preserve_config:` 는 `config` 로 승격한다. 승격 결과는 `--dry-run` 에 찍는다(#P002 `[D06]` 과 같은 규칙).

⚠️ 이름에 **공백·쉼표·세미콜론·와일드카드 금지** 규칙은 그대로다. 스크립트가 그 자리에서 목록을
쪼개므로 갈라진 이름은 "이전 배포본에 없음"으로 건너뛰어지고 — **배포는 성공하고 데이터만 사라진다.**

### 스크립트는 분류를 모른다

`[D10]` 경계를 지킨다. Node 가 분류를 해석해 **용도별 목록을 따로 넘기고**, 스크립트는 받은 목록대로만
움직인다. 분류 이름이 bat 안에 들어가면 정책이 스크립트로 새고 테스트가 불가능해진다.

| 스크립트 변수 | 받는 것 | 시점 |
|---|---|---|
| `DP_EXCLUDE` | copy 모드에서 복사 제외할 이름 = **`config` 만** (§3.1) | 복사 |
| `DP_DELTA` | swap 모드에서 `_org_` → 새 라이브로 따라잡을 이름 = `temp` + `data` | 스왑 후 · 시작 전 |
| `DP_PRESERVE` | (현행) 옛 빌드 → 새 빌드 이월. **벌크가 정지 전으로 옮겨가면 `DP_DELTA` 로 대체된다** | 폐지 예정 |

벌크 이월(`_preserve_<stamp>` → 임시폴더)과 백업은 **정지 전이라 Node 가 한다.** 스크립트는
정지 구간 안의 일(스왑 · 델타 · 시작)만 맡는다 — `[D10]` 경계 그대로다.

### 3.1 copy 모드에서 제외는 `config` 하나뿐이다

`data`·`temp` 는 **산출물에 없다.** 운영 중 서버에서 생긴 것이라 빌드 결과에 들어갈 일이 없고,
robocopy 는 미러(`/MIR`)가 아니면 원본에 없는 파일을 지우지 않는다(#P003-OQ2 에서 미러 배제 확정).
→ 제외 목록에 적을 이유가 없다. 적으면 **없는 위험을 막는 설정**이 되어 읽는 사람을 헷갈리게 한다.

`config` 는 다르다. **산출물에 같은 이름의 파일이 들어 있을 수 있다.** 제외하지 않으면
산출물의 `web.config` 가 서버 설정을 덮는다 — 스왑의 Step 2.5(라이브 설정을 임시폴더로)가
막아 주던 사고다. **copy 모드에서는 `DP_EXCLUDE` 가 그 Step 2.5 를 대신한다.**
지금은 `exclude:` 가 빌드 산출물에서 설정을 지워 사고가 나지 않지만, 그 설정이 빠진 프로젝트에서는 바로 터진다.

### 3.2 copy 모드는 preserve 를 임시폴더로 복원하지 않는다

"스왑과 같은 소스 구성"(임시폴더 = 산출물 + preserve)을 copy 에도 적용하면 두 가지가 생긴다.

* **데이터가 되돌아간다.** 백업은 정지 **전**에 뜬다. 백업~정지 사이에 들어온 업로드는 백업본에 없고,
  그 백업본을 라이브에 덮으면 **그 사이 데이터가 사라진다.** copy 는 라이브를 그대로 두므로
  원래 없던 위험이다.
* **대용량 왕복.** 임시폴더는 매번 새 폴더라 증분이 없다. `라이브 → 임시 → 라이브` 로
  전량 복사가 두 번 일어난다. swap 은 폴더가 통째로 바뀌니 한 번은 불가피하지만 copy 는 0 이다.

## 4. 백업과 롤백 — `#P003-OQ1` 확정

**백업은 라이브 폴더 사본이 아니다. `유지파일 + 배포 zip` 두 조각이다** (2026-09-23 보스 확정).

| 조각 | 무엇 | 크기 | 역할 |
|---|---|---|---|
| `<live>_preserve_<stamp>` | `temp`·`data`·`config` 분류 항목 | 작다 | 운영 데이터 보호 |
| `<name>_<stamp>.zip` (확정본) | 빌드 산출물 | 약 240MB (폴더 690MB 의 1/3) | **롤백 원본** |

**롤백 = 확정된 이전 zip 을 다시 전개한다.** 배포와 같은 경로를 타므로 검증되지 않은 길이 없다.
유지파일은 되돌리지 않는다 — 기존 규칙 그대로다(*"롤백은 코드를 옛것으로 되돌릴 뿐 데이터는 현재 것"*).

### 배포 흐름 (보스 예시)

```
배포폴더 ./project1 · 배포파일 project1.zip · 해제폴더 ./temp_project1

copy   ① 백업   유지파일 -> ./project1_preserve_<stamp>
       ② 복사   ./temp_project1 + 유지파일 -> ./project1
       성공     preserve 백업 확정 · zip 확정 · ./temp_project1 삭제

swap   ① 백업   유지파일 -> ./project1_preserve_<stamp>
       ② 복사   ./temp_project1 + 유지파일
       ③ 스왑   ./project1 -> ./project1_org · ./temp_project1 -> ./project1
       성공     preserve 백업 확정 · zip 확정 · ./project1_org 삭제
       실패     역순 — ./project1 -> ./temp_project1 · ./project1_org -> ./project1
```

### 성립 조건 셋

1. **zip 에 세대가 필요하다.** 지금은 [ArchiveStage.js:41-49](../../../../src/deploy/stages/ArchiveStage.js#L41-L49)
   가 고정 이름으로 덮어쓰므로, 배포 시점의 `project1.zip` 은 **이미 새 빌드**다. 되돌릴 대상은
   직전 성공 배포의 zip이다 → "확정"에서 스탬프를 붙여 남긴다. 세대 수 = `--rollback=N` 상한.
2. **확정 zip 은 배포서버(원격)에 둔다.** 롤백 때 재업로드가 없다. 이미 `upload_path` 에 올라가 있고,
   [RemoteDeployMacroStage.js:302](../../../../src/deploy/stages/RemoteDeployMacroStage.js#L302) 가
   `remoteFile` 을 정리 함수로 넘기는데 [:322](../../../../src/deploy/stages/RemoteDeployMacroStage.js#L322)
   에서 **받지 않는다** — 자리는 이미 있다.
3. **"확정" 시점은 헬스체크 통과 후다.** 스왑 직후가 아니다.

### 보완 (아토 제안)

* **`<live>_org` 삭제는 헬스체크 뒤로.** 스왑 직후에 지우면 헬스체크 실패 시 복구가 zip 전개(수십 초)뿐이다.
  `_org` 가 남아 있으면 역스왑 몇 초다. 비용은 한 사이클치 디스크뿐이다.
* **preserve 백업은 `backup_root` 에 둔다.** 라이브 옆에 두면 현재 정리 로직이 인식하지 못해
  **영원히 누적된다** — 패턴이 `<라이브명>_<14자리시각>` 이다
  ([backupRetention.js:32-35](../../../../src/deploy/backupRetention.js#L32-L35)). 시각도 그 규약을 따른다.
* 확정 zip 의 정리도 같은 보관 정책(`backup.keep_count`)을 쓴다. 폴더용 `selectFromNames` 에
  **파일(.zip) 변형**이 필요하다.

## 5. 종료코드 확장

copy 모드에는 스왑에 없던 상태가 하나 생긴다 — **라이브가 반쯤 덮인 상태**.
[scriptExit.js](../../../../src/deploy/scriptExit.js) 의 `DEPLOY` 표에서 `1` 과 `5` 의 뜻이 갈리는 자리와 같은 성격이다.

| 코드 | swap | copy |
|---|---|---|
| `0` | 배포됨 | 배포됨 |
| `1` | 라이브는 이전 빌드로 살아 있다 (되돌렸거나 옮기기 전) | **복사 시작 전에 실패** — 라이브 그대로 |
| `5` | 되돌리지 못했다. 라이브 폴더가 없다 | **복사 도중 실패 — 라이브가 섞였다.** 백업에서 복구해야 한다 |

`5` 는 두 방식 모두 "사람이 개입해야 하는 상태"라는 뜻을 유지한다.
Node 의 롤백 무장 판단(`0`·`5`·미지코드는 무장)도 그대로 성립한다.
