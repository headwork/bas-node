# 4. 젠킨스 잡

배포서버(젠킨스)에서 파이프라인을 돌리는 잡 구성. 실행 대상은
[운영 배포 흐름](02_운영_배포_흐름.md)의 배포서버 구간이다.

기존 젠킨스 구성은 `hlngsGitPull` → `hlngsBuildWesys` → `hlngsUpload` → `telegram`
네 개의 잡을 `plDeployWesysTest` 가 순서대로 부르는 형태였다. 새 구성은 **잡 하나**다 —
순서와 조건 분기가 잡 사이가 아니라 **YAML 안**에 선언으로 들어가기 때문이다.

---

## 배치물

번들 빌드(`npm run build-prod`)의 산출물 `dist` 가 **배포 패키지 전체**다. 그대로 배포서버
한 곳에 복사한다. `node_modules` 는 필요 없다 — 의존성이 `bas-library.js` 에 들어 있다.

`dist` 는 빌드마다 통째로 지우고 다시 만든다. 번들이 아닌 파일(런처·스크립트·설정·LICENSE)은
[bundle_config/deploy/](../../../bundle_config/deploy/) 가 원본이고 빌드가 복사해 넣는다.
**`dist` 에서 고치면 다음 빌드에 사라진다.** `dist` 는 git 추적 대상이 아니다.

```
D:\Deploy\bas-deploy\               (= TOOL_HOME)
  ├─ bas-deploy.js            배포 CLI 번들                 ┐ webpack
  ├─ bas-library.js           공유 청크. 같은 폴더에 있어야 한다 │
  ├─ bas-library.js.LICENSE.txt                              ┘
  ├─ basDeploy.bat            실행 런처                     ┐ bundle_config/deploy
  ├─ gitAskpass.bat           git 자격증명 응답기             │
  ├─ LICENSE                                                  │
  ├─ config\                  app.json · <project>.json     │
  └─ script\windows\          deploy.bat · rollback.bat · webserver_iis.bat ┘
```

파이프라인 정의(`deploy_*.yaml`)는 도구 폴더가 아니라 프로젝트 폴더(`D:\Deploy\<프로젝트>\config`)에
둔다 — [06_배포_스크립트_규약.md §8](06_배포_스크립트_규약.md).

> ⚠️ `config\<project>.json` 은 **서버마다 다르다**(젠킨스 주소·토큰). 저장소에는 샘플만
> 추적하고 실물은 로컬에만 있다. 다른 서버(`jenkins_dev` 등)에 배치할 때는 `config\` 를 빼고
> 복사한다 — 통째로 덮으면 그 서버의 설정이 이 PC 의 것으로 바뀌는데 에러는 나지 않는다.

`basDeploy.bat` 은 `NODE_HOME`(디렉터리·exe 경로 모두 허용)을 쓰고, 없으면 PATH 의
`node` 로 떨어진다. 서버마다 노드 설치 경로가 달라 박아두지 않았다.

## 자격증명 — `git_wesys`

**URL 에 자격증명을 넣지 않는다.** `GIT_ASKPASS` 로 넘긴다.

```groovy
withCredentials([usernamePassword(credentialsId: 'git_wesys',
                                  usernameVariable: 'GIT_USER',
                                  passwordVariable: 'GIT_PASS')]) {
    bat '...'
}
```

`GIT_ASKPASS` 가 가리키는 `gitAskpass.bat` 이 git 의 프롬프트를 보고 답한다.

```bat
echo %* | findstr /I "Username" > nul
if errorlevel 1 ( echo %GIT_PASS% ) else ( echo %GIT_USER% )
```

**코드 변경이 필요 없다.** [PipelineEngine.js:382](../../../src/deploy/PipelineEngine.js#L382)
의 `execSync` 가 `env` 를 따로 주지 않아 `process.env` 를 그대로 상속하고,
`git_sync` 가 부르는 `git` 이 그 환경변수를 읽는다.

### 왜 URL 삽입 방식을 쓰지 않는가

```js
// 쓰지 않는다
const repoUrl = `https://${user}:${pass}@host/repo.git`;
execSync(`git clone ${repoUrl}`);
```

| 문제 | 내용 |
|---|---|
| **인증 실패** | Git 서버가 **Bonobo Git Server** 다. URL 자격증명이 GCM·젠킨스에 등록된 정상 자격을 덮어써서 **인증이 깨진다** ([README](README.md#민감-정보)에 기록된 사례) |
| **디스크 잔존** | `clone` 이 자격증명째로 `.git/config` 의 remote URL 에 적어 넣는다. 이후 `git remote -v` 에 그대로 보인다 |
| **프로세스 노출** | 커맨드라인에 남아 같은 장비의 다른 프로세스에서 보인다. 젠킨스가 가리는 것은 **콘솔 출력뿐**이다 |

> ⚠️ `git_url` 이 `http://112.217.163.10:16784/WeSys.git` 로 **평문 HTTP** 다.
> Basic 인증은 base64 일 뿐 암호화가 아니라 네트워크 구간에서 그대로 읽힌다.
> 사내망 전제이지만, HTTPS 전환은 별도 과제로 남는다.

## 환경 전환

`--params` 로 넘긴다. **`${env.VAR}` 로는 안 된다** — 프로파일 선택이 변수 치환보다
먼저 일어나서 `environment: "${env.DEPLOY_ENV}"` 는 치환되지 않은 문자열 그대로
프로파일을 찾는다.

```
Pipeline failed with error: Target profile '${env.DEPLOY_ENV}' not found in YAML. Available: qa, prod
```

조용히 넘어가지 않고 즉시 실패하므로 잘못 쓸 위험은 없지만, 동작하지 않는다.

**젠킨스 `bat` 에서 통하는 형태는 이스케이프한 쪽이다.** 빌드 #1 로 확인했다.

```bat
rem O
--params="{\"environment\":\"prod\"}"

rem X — cmd 가 따옴표를 구분자로 먹어 {environment:prod} 가 되고 Invalid JSON 으로 죽는다
--params={"environment":"prod"}
```

셸에 따라 따옴표가 한 겹 더 남는 경우가 있어 [deploy-cli.js](../../../src/deploy/deploy-cli.js)의
`parseParams` 가 둘 다 받아낸다. 다만 **틀린 형태는 조용히 넘어가지 않고 멈춘다** —
예전에는 `JSON.parse` 가 객체 대신 **문자열**을 돌려줘도 예외가 없어서, 그 문자열이
엔진에서 한 글자씩 펼쳐지고(`0={`, `1="`, `2=e` …) environment 오버라이드가 사라졌다.
**`prod` 를 골라도 `qa` 로 배포되는데 아무 경고가 없었다.**

## Jenkinsfile — `plDeployNode`

그룹마다 젠킨스 stage 를 하나씩 둔다. 어디서 실패했는지가 stage view 에 바로 보인다.

> ⚠️ `agent { label 'windows' }` 로 쓰지 않는다. **이 젠킨스에는 에이전트 노드가 없고**
> (`jenkins_home\nodes` 없음) 내장 노드의 라벨도 비어 있다(`config.xml` 의 `<label></label>`).
> 라벨을 걸면 빌드가 시작되지 않고 큐에 매달린다. 라벨을 붙이려면 먼저 내장 노드에
> `windows` 라벨을 부여할 것.

```groovy
pipeline {
    agent any                          // 내장 노드에 라벨이 없다. 라벨을 걸면 큐에 매달린다

    options {
        timestamps()
        disableConcurrentBuilds()          // 같은 잡의 중복 실행을 큐에 세운다
        buildDiscarder(logRotator(numToKeepStr: '30'))
    }

    parameters {
        choice(name: 'DEPLOY_ENV', choices: ['qa', 'prod'], description: '배포 대상 환경')
        booleanParam(name: 'DRY_RUN', defaultValue: false, description: '계획만 출력하고 실행하지 않는다')
    }

    environment {
        TOOL_HOME   = 'D:\\Deploy\\bas-deploy'
        // 전체경로. 상대경로가 통하는 것은 basDeploy.bat 이 자기 폴더로 cd 하기 때문이라,
        // 런처를 고치면 조용히 깨진다. 실행 위치에 의존하지 않게 박아 둔다.
        YAML        = 'D:\\Deploy\\hlngs\\config\\deploy_shore.yaml'   // 프로젝트 폴더 (06_ §8)
        GIT_ASKPASS = 'D:\\Deploy\\bas-deploy\\gitAskpass.bat'
        DEPLOY_KEY  = "${env.BUILD_TAG}"    // 젠킨스가 주는 실행 식별자를 그대로 쓴다
    }

    stages {
        // script 로 감싼다 — Declarative 의 steps 는 스텝만 받아서
        // 임의 메서드를 그냥 부르면 "Expected a step" 으로 걸릴 수 있다.
        stage('git check') { steps { script { runGroup('git_check') } } }
        stage('build')     { steps { script { runGroup('build') } } }
        stage('deploy')    { steps { script { runGroup('deploy') } } }
    }

    post {
        always {
            // Abort 로 죽어도 이 블록은 돈다. 락이 남지 않게 여기서 푼다.
            // returnStatus 로 받는다 — 뒷정리 실패가 성공한 배포를 뒤집으면 안 된다.
            script {
                def rc = bat(returnStatus: true,
                    script: "\"%TOOL_HOME%\\basDeploy.bat\" --yaml=%YAML% --unlock --deploy-key=%DEPLOY_KEY%")
                if (rc != 0) {
                    echo "경고: 락 해제 실패 (rc=${rc}). --status 로 확인하고 필요하면 --force-unlock."
                }
            }
        }
        failure {
            echo "배포 실패 - rollback 이 이미 실행되었다. 로그의 [Rollback] 구간을 확인할 것."
        }
    }
}

// pipeline 블록 바깥에 정의한다. 호출부가 이미 script 안이므로 여기서 또 감싸지 않는다.
void runGroup(String group) {
    withCredentials([usernamePassword(credentialsId: 'git_wesys',
                                      usernameVariable: 'GIT_USER',
                                      passwordVariable: 'GIT_PASS')]) {
        def dry = params.DRY_RUN ? ' --dry-run' : ''
        bat "\"%TOOL_HOME%\\basDeploy.bat\" --yaml=%YAML%" +
            " --only=${group} --deploy-key=%DEPLOY_KEY%" +
            " --params=\"{\\\"environment\\\":\\\"${params.DEPLOY_ENV}\\\"}\"" + dry
    }
}
```

### 단계를 나누면 상태가 끊긴다 — `--deploy-key` 가 그것을 잇는다

젠킨스 stage 마다 **프로세스가 새로 뜬다.** `git_sync` 가 판정한
`changed_static_only` 는 그 프로세스와 함께 사라지고, 다음 단계에서는 `undefined` 가
된다. 그러면 `unless: changed_static_only` 가 통과해 **정적 파일만 바뀌었는데도 전체
빌드가 도는데, 에러가 나지 않는다.**

같은 `--deploy-key` 를 넘기면 상태 파일에서 이어받는다. 잇지 못하는 상황은 **실패로
멈춘다** — 조용히 빈 상태로 시작하지 않는다.

```
이어받을 상태가 없습니다 (key=..., group=build).
  첫 그룹은 'git_check' 입니다. 앞 단계가 실행되지 않았거나 --deploy-key 가 다릅니다.
```

### 중복 실행 방지 — 방어선 둘

| 방어선 | 막는 것 |
|---|---|
| `disableConcurrentBuilds()` | 같은 잡의 중복 빌드 |
| 도구의 **파일 락** | 젠킨스 밖에서 들어오는 수동 실행, 다른 잡, 그룹 사이의 틈 |

락은 상태 JSON 과 **다른 파일**이다(`<state>/<yaml>.<env>.lock`). JSON 을 읽고-고치고-쓰는
것은 원자적이지 않아 두 프로세스가 동시에 "잠기지 않음"을 읽을 수 있다. 락은
`fs.openSync(path, 'wx')` 로만 잡는다.

> ⚠️ **락의 주인은 프로세스가 아니라 실행(run)이다.** 그룹 사이에는 프로세스가 없으므로
> pid 생존으로 판정하면 매번 남의 락을 깬다. 자동 해제는 상태 파일의 그 실행이
> `running` 이 아닐 때만 한다. 살아 있는 실행은 TTL 이 지나도 깨지 않고 경고만 남긴다.

### 중간에 멈추기

| 방법 | 동작 |
|---|---|
| `--cancel --deploy-key=<키>` | 취소를 요청한다. **다음 스테이지 경계에서** 깨끗이 멈춘다. 진행 중인 압축을 끊지는 못한다 |
| 젠킨스 **Abort** | 프로세스 트리 강제 종료. 정리 코드가 돌지 않으므로 `post{always}` 의 `--unlock` 이 필요하다 |
| `--force-unlock` | 보유자와 무관하게 락 해제. 사람이 판단해서 쓴다 |
| `--status` | 현재 락 보유자와 최근 실행 5건 |

### 왜 잡을 나누지 않는가

기존은 `git pull` · `빌드` · `업로드` 가 각각 잡이었다. 새 구성에서 그 순서는
`stages:` 목록이고, "정적 파일만 바뀌면 빌드를 건너뛴다" 같은 분기는 `if:` / `unless:` 다
([정적파일 빠른배포](03_정적파일_빠른배포.md)).

잡을 쪼개면 **분기가 젠킨스 설정 화면으로 흩어진다.** 무엇이 어떤 조건에 도는지가
UI 를 눌러봐야 보이고, 코드리뷰에 걸리지 않으며, 다른 환경으로 복제할 때 손으로 옮겨야 한다.
YAML 한 파일로 두면 diff 에 남는다.

젠킨스가 계속 담당하는 것은 **스케줄 · 자격증명 보관 · 실행 이력**이다.

## 배포 공지 (텔레그램)

기존 `telegram` 잡이 하던 일을 파이프라인이 직접 한다. 잡 체인의 마지막 칸이었던 것이
YAML 스위치 하나로 바뀌었다. 내용도 달라졌다 — 기존은 `[QA]서버 배포!` 한 줄이었고,
지금은 **무엇이 배포됐는지**를 싣는다.

```
[WESYS-QA] 배포
변경내용======================
46335127e 차입금 상환 도래 Notice 메일 알림 기능 개발, {doc_no:26PTSM00875 }

변경파일======================
MFM.Common/MFM.Biz.Base/Service/EmailSendService.cs
... 외 3건
```

**보낼지**는 YAML 이, **어떻게 보낼지**는 config 가 정한다. yaml 은 프로젝트를 따라다니고
config 는 서버에 남으므로, 서버마다 다른 것(잡 이름·접속정보·토큰)을 yaml 에 두지 않는다.

| 무엇 | 어디 |
|---|---|
| 보낼지 말지 | YAML `target.<환경>.telegram: true` |
| 머리말(`WESYS`) | YAML `notify_tag`. 생략 시 `project` 대문자 |
| 보내는 길 | `config/<project>.json` 의 `telegram.job_name` — 아래 |
| 토큰·채팅방 | 같은 파일의 `telegram.token` · `telegram.chat_id` (직접 경로에서만) |
| 재료(커밋·파일) | `git_sync` 가 만들어 상태 파일에 넣어 둔 것 |

### 보내는 길 두 가지

`telegram.job_name` 이 있으면 **젠킨스 잡**을 부르고, 비어 있으면 도구가 **텔레그램 API 를
직접** 친다. 도착지는 같고 다른 것은 토큰이 어디 있느냐다.

| | 잡 경유 (`job_name` 있음) | 직접 (`job_name` 없음) |
|---|---|---|
| 봇 토큰 | 젠킨스 자격증명 안에만 | 배포 도구가 들고 있어야 한다 |
| 젠킨스 없이 | 못 보낸다 | 보낸다 |
| 실패가 드러나는 곳 | 큐 적재 응답 + 잡 빌드 로그 | 배포 로그 |

잡을 부를 젠킨스는 `telegram.job_server` 가 가리키는 블록(`jenkins` 기본, `jenkins_dev` 등)의
`URL`·`USER`·`API_TOKEN` 을 쓴다.

> ⚠️ **잡과의 계약은 파라미터 이름 세 개로 고정한다.** 잡을 새로 만들 때도 이 이름을 쓴다.
>
> | 파라미터 | 값 |
> |---|---|
> | `TAG_DEPLOY` | `QA` \| `PROD` — 잡의 choice 목록. `prod` 만 `PROD` 로 가고 나머지 환경은 `QA` 로 접는다 |
> | `MSG` | 본문 |
> | `FILE_PATH` | 첨부 경로. 배포 공지는 비워 보낸다 |
>
> choice 목록에 없는 값을 보내면 젠킨스가 파라미터를 만들지 못하고 **500** 으로 되튄다.
> 어느 환경인지는 본문 머리말(`[WESYS-QA]`)이 이미 정확히 말해 준다.
>
> 큐에 넣는 것까지만 확인하고 빌드 결과는 기다리지 않는다 — 공지 하나로 배포를 붙잡지
> 않는다. 잡 이름 오타(404)와 파라미터 불일치(500)는 큐 적재 시점에 드러나므로 흔한
> 실패는 여기서 잡힌다.

### 직접 경로를 쓸 때 — 토큰 주입

토큰은 파일에 적지 않는다. 잡에서 자격증명을 환경변수로 주입한다.

```groovy
environment {
    TOOL_HOME      = 'D:\\Deploy\\bas-deploy'
    GIT_ASKPASS    = "${TOOL_HOME}\\gitAskpass.bat"
    YAML           = "${TOOL_HOME}\\deploy_shore.yaml"
    DEPLOY_KEY     = "${env.BUILD_TAG}"
    TELEGRAM_TOKEN = credentials('telegramToken')   // config 의 ${env.TELEGRAM_TOKEN} 이 이걸 받는다
}
```

> ⚠️ `credentials()` 는 **없는 ID 를 참조하면 빌드가 실패한다.** 그 젠킨스에 `telegramToken`
> 자격증명이 등록돼 있는지 먼저 확인할 것. 운영 젠킨스에는 있고(기존 `telegram_v1` 이 쓴다),
> 로컬 테스트 젠킨스에는 없다.
>
> 잡 경유로 쓰면 이 주입 자체가 필요 없다 — 토큰은 공지 잡만 안다.

> ⚠️ 설정 로더는 값이 없는 `${env.X}` 를 **원문 그대로 남긴다**(`config/index.js` expandEnv).
> 비어 있지 않으니 존재 검사는 통과하고, 그 문자열이 토큰인 척 전송에 실린다.
> `notify.js` 의 `missing()` 이 이걸 걸러 이유를 로그에 남긴다.

### 부르는 자리가 스테이지가 아닌 이유

`stages:` 에 두면 **실패했을 때 공지가 가지 않는다.** 실패하면 스테이지 목록을 끝까지 돌지
않기 때문이다. 특히 라이브를 건드리기 전에 깨지면(빌드 실패 등) `rollback:` 조차 돌지 않아서,
거기 넣어 두어도 소용이 없다 — 2026-09-04 의 빌드 실패 두 건이 정확히 그 모양이었다.

그래서 파이프라인 **종료 지점**에서 부른다. 성공은 마지막 그룹에서 한 번, 실패는 어느
그룹에서 깨졌든 한 번. 상태 파일의 `announced` 표식이 중복 발송을 막는다.

공지 실패는 배포 결과를 바꾸지 않는다. 삼키고 경고만 남긴다.
