# 5. 신규 프로젝트 배포 설정

새 프로젝트를 배포 파이프라인에 태울 때 **개발자에게 받는 정보**와,
그 답이 YAML 어디로 가는지의 대응표다.

- **1부**는 개발자가 채운다. YAML 을 몰라도 된다.
- **2부**는 받은 답으로 YAML 을 만드는 사람이 본다.
- 골격은 [deploy_sample.yaml](../template/deploy_sample.yaml) 을 복사해서 쓴다.

예시는 **wesys**(`MFM.Shore`) 기준이다. 접속정보·계정·도메인은 `*` 로 가렸다.

---

# 1부 · 접수 양식

> 모르는 항목은 **비워 두고 "모름"** 이라고 적는다.
> 추측해서 채운 값은 빈칸보다 나쁘다 — 틀려도 에러가 안 나는 항목이 섞여 있다.

## 1. 프로젝트 정보

| 항목 | 설명 | wesys 예시 |
|---|---|---|
| **프로젝트명** | 부르는 이름 | `MFM.Shore` (wesys) |
| **git 저장소** | URL. 계정·비번은 적지 말 것 | `http://***.***.***.**:*****/WeSys.git` |
| **배포 브랜치** | 환경마다 다르면 전부 | 개발·QA `deploy/qa` / 운영 `master` |
| **프로젝트 폴더** | 저장소 안에서 **빌드를 실행할 위치** | `MFM.Shore/Web` |
| **빌드 방법** | 도구와 명령 | `dotnet build MFM.Shore.csproj -c Release` (게시 프로파일 사용) |
| **빌드 결과물 위치** | ★ 빌드하면 **실제로 어디에 떨어지는지** | `D:\Deploy\build\MFM.SHORE_QA` |
| **특이사항** | 아래 참고 | .NET 6, 게시 프로파일(pubxml)이 출력 경로를 들고 있음 |

**특이사항에 적을 만한 것**

- 빌드 전에 해야 하는 것 (`npm ci`, 패키지 복원, 코드 생성 등)
- 빌드 도구 버전 제약 (.NET 6, Node 18 …)
- 빌드가 오래 걸리는지 (수 분 이상이면 미리 알아야 한다)
- 빌드 산출물 크기 (수백 MB면 압축·전송 시간이 붙는다)
- 환경마다 빌드가 다른지 (프로파일·설정 분기)

> ★ **빌드 결과물 위치는 반드시 실물로 확인해서 적는다.**
> 빌드 도구가 자체 설정으로 출력 위치를 정하는 경우(.NET 의 `pubxml` `PublishUrl` 등),
> 그 값과 파이프라인이 보는 경로가 어긋나면 **빌드는 성공하는데 낡은 산출물이 배포된다.**
> 에러가 나지 않으므로 몇 주간 정상으로 보인다. 2026-09-04 QA 에서 실제로 걸렸다.

## 2. IIS 배포 정보

환경(개발·QA·운영)마다 다르면 **환경별로** 적는다.

| 항목 | 설명 | wesys 예시 (QA) |
|---|---|---|
| **배포 서버** | 어느 장비인지. 접속 방법(SSH) 가능 여부 | `***.***.**.***` (SSH 포트 `****`) |
| **서비스명** | IIS 사이트/앱풀 이름 | `MFM.SHORE_QA` |
| **배포 폴더** | IIS 가 바라보는 **라이브 경로** | `D:\Deploy\MFM.SHORE_QA` |
| **업로드 폴더** | 압축본이 도착할 폴더 | `D:\<업로드>\build` |
| **백업 폴더** | ★ 배포 폴더와 **같은 드라이브** | `D:\<업로드>\backup` |
| **환경설정 파일** | 서버마다 값이 다른 파일 목록 | `web.config`, `appsettings.json` |
| **상태 확인 URL** | 배포 성공 판정 기준 | `https://****.***.co.kr/healthz` |
| **특이사항** | 아래 참고 | — |

**특이사항에 적을 만한 것**

- 서비스 정지·시작에 특별한 절차가 있는지 (예약작업, 워커, 큐 소비자 등)
- 배포 중 끊기면 안 되는 것이 있는지
- 배포 후 확인해야 할 화면·기능
- 접근 제한 (방화벽, VPN, 특정 계정만 가능)
- IIS 가 아닌 것 (Windows 서비스, 리눅스 등)

> ★ **백업 폴더는 배포 폴더와 같은 드라이브**여야 한다.
> 백업은 폴더 이름만 바꿔 치우는 방식(rename)이라, 드라이브가 다르면 전체 복사가 되어
> 수 분씩 걸리거나 실패한다.

> ★ **환경설정 파일은 최초 1회 사람이 넣어야 한다.**
> 배포는 폴더를 통째로 갈아끼우므로, 목록에 적은 파일은 라이브에서 새 배포본으로 옮겨진다.
> 라이브에도 백업에도 없으면 **배포를 실패시킨다** — 설정 없는 배포본이 라이브가 되는 것보다 낫다.

## 3. 환경 목록

배포할 환경을 적는다. 환경마다 위 2번 정보가 따로 필요하다.

| 환경 | 브랜치 | 배포 서버 | 원격/로컬 | 배포 알림 |
|---|---|---|---|---|
| 개발 | `deploy/qa` | 빌드서버 자신 | 로컬 | 안 함 |
| QA | `deploy/qa` | `***.***.**.***` | 원격 | 안 함 |
| 운영 | `master` | `***.***.**.***` | 원격 | 보냄 |

## 4. 배포 알림 (선택)

| 항목 | 설명 | wesys |
|---|---|---|
| 알릴 환경 | 보통 운영만. 전부 켜면 소음이 된다 | 운영 |
| 텔레그램 채팅방 | chat_id | `-100***` |
| 봇 토큰 | **파일에 적지 않는다** — 젠킨스 자격증명으로 | `telegramToken` |
| 공지 머리말 | `[WESYS-QA]` 의 앞부분 | `WESYS` |
| 공지 잡 | 있으면 그 잡을 거쳐 보낸다. 없으면 도구가 직접 보낸다 | `telegram_v2` |

커밋 목록과 변경 파일은 파이프라인이 알아서 싣는다. 형식과 동작은
[04_젠킨스_잡.md](04_젠킨스_잡.md) 의 "배포 공지" 절에 있다.

**보낼지**만 YAML 이 정하고(`target.<환경>.telegram`), **어떻게 보낼지**는 전부
`config/<프로젝트키>.json` 의 `telegram` 블록이 쥔다. 잡 이름·접속정보·토큰은
서버마다 다른 인프라 정보라, 프로젝트를 따라다니는 YAML 에 두지 않는다.

기존 공지 잡을 재사용하려면 **파라미터 이름이 `TAG_DEPLOY`(QA\|PROD) · `MSG` · `FILE_PATH`**
여야 한다. 다르면 잡을 고치거나 새로 만든다.

# 2부 · YAML 대응표

받은 답이 [deploy_sample.yaml](../template/deploy_sample.yaml) 어디로 들어가는지.

| 접수 항목 | YAML 위치 |
|---|---|
| git 저장소 | `git_url` (자격증명 제거) |
| 배포 브랜치 | `target.<환경>.branch` |
| 프로젝트 폴더 | `server_list.<빌드서버>.build_cwd` |
| 빌드 방법 | `server_list.<빌드서버>.build_cmd` → **스크립트 파일**로 분리 |
| 빌드 결과물 위치 | `target.<환경>.build_path` |
| 배포 서버 | `server_list.<배포서버>.ssh.host` · `port` |
| 서비스명 | `server_list.<배포서버>.iis_site` |
| 배포 폴더 | `server_list.<배포서버>.web_deploy_path` |
| 업로드 폴더 | `server_list.<배포서버>.upload_path` |
| 백업 폴더 | `server_list.<배포서버>.backup_root` |
| 환경설정 파일 | `exclude` + `preserve_config` |
| 상태 확인 URL | `server_list.<배포서버>.health_url` |
| 환경 목록 | `target.<환경>` 블록 |

## 받는 쪽이 따로 정하는 것

접수 양식에 없지만 YAML 에 필요한 값들. 개발자에게 묻지 않는다.

| 항목 | 기본 판단 |
|---|---|
| 프로젝트 키 · `config/<키>.json` | 프로젝트명에서 정한다. `app.json` 의 `projects[]` 에도 추가 |
| 상태파일 위치 (`state_path`) | 기존 프로젝트와 같은 폴더 |
| 백업 보관 수 (`keep_count`) | 3 — 그대로 `--rollback=N` 의 상한이 된다 |
| 압축 여부 (`compress`) | 원격은 강제 true, 로컬은 false |
| 젠킨스 잡 · 자격증명 ID | 운영 젠킨스에 생성 |
| 공지 잡 (`telegram.job_name`) | 기존 공지 잡을 재사용한다. 파라미터 이름이 다르면 새로 만든다 |
| SSH 계정·키 | `~/.ssh/config` 에 Host 등록 (YAML 에 적지 않는다) |

## 사전 준비 — 사람이 미리

- [ ] 원격에 업로드·백업 폴더 생성
- [ ] IIS 사이트 생성, 배포 폴더를 physicalPath 로 지정
- [ ] 환경설정 파일 최초 배치
- [ ] SSH 키 접속 확인
- [ ] 상태 확인 URL 응답 확인
- [ ] 젠킨스에 git 자격증명 등록

## 첫 실행

```
1. --dry-run 으로 해석된 변수를 눈으로 확인   ← 경로가 전부 보인다
2. 개발(로컬) 환경 실배포
3. QA 실배포
4. --status 로 이력·락 확인
```

**잡을 처음 걸 때는 반드시 `--dry-run` 을 한 번 돌리고 값을 확인한다.**
특히 `build_cmd` 와 `web_deploy_path` 는 여기서 못 잡으면 실배포가 라이브를 건드린다.

# 부록 · 조용히 실패하는 자리

에러가 나지 않으므로 **찾아서 봐야** 하는 것들이다.
자세한 배경은 [04_젠킨스_잡.md](04_젠킨스_잡.md) 와 각 소스 주석에 있다.

| 자리 | 증상 |
|---|---|
| 빌드 산출물 경로 불일치 | 빌드 성공, **낡은 산출물이 배포**된다 |
| `${env.VAR}` 미정의 | 빈 문자열로 치환. 자격증명이면 "인증 실패"만 남는다 |
| `git_url` 에 자격증명 삽입 | Bonobo 에서 정상 자격을 덮어써 인증이 깨진다 |
| `target` 의 `<<:` 머지키 | 아무것도 병합되지 않는다 (`server_list` 에서만 동작) |
| `--params` 인용 오류 | environment 오버라이드가 무시된다 |
| `--deploy-key` 누락·불일치 | 앞 단계 판정이 `undefined` 가 되어 조건이 통과한다 |
| 젠킨스 파라미터를 UI 에서만 수정 | 다음 빌드에 스크립트 값으로 되돌아간다 |
| `DEPLOY_ENV` 선택지 첫 항목 | 그것이 기본값이다. 운영을 앞에 두지 않는다 |
| 백업 루트 공유 | 다른 파이프라인의 백업을 정리 대상으로 본다 |
| 성공 신호 액면 수용 | **0건 통과는 통과가 아니다.** 실행 건수·산출물 크기를 본다 |
